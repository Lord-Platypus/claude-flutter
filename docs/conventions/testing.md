# Testing Conventions

Read this **before writing or modifying tests** under `test/`.

---

## 1. Zero Tolerance: All Tests Green

Never declare a task as complete if any test fails. After every code change run
`flutter test test/features/<feature_name>/`. If anything red — fix before moving on.

```bash
flutter test
flutter test test/features/<feature_name>/
flutter test test/features/<feature_name>/domain/usecases/<usecase>/<usecase>_usecase_test.dart
flutter test --coverage
```

---

## 2. What Mason-Generated Tests Cover (structural wiring)

- **Usecase tests** (`new_usecase_test`): usecase delegates to the repository method. Both
  `DataSuccess` and `DataFailed` paths are tested.
- **Repository tests** (`new_repository_test`): `RepositoryImpl` delegates to
  `LocalDatasource`. Each method tested for `DataSuccess` on success and `DataFailed` when
  the datasource throws.
- **BLoC tests** (`new_bloc_test`): BLoC initial state, `Started` event emits `Loading`.
  Custom event handlers scaffolded as commented-out test stubs for the agent to fill in.
  Uses `flutter_test` + `mocktail` (not `bloc_test` — incompatible with `floor_generator`).

---

## 3. What Requires Manual Tests

- Domain-specific edge cases and validation logic.
- Complex state interactions in BLoCs (multi-event sequences, conditional transitions).
- Custom widget behaviour beyond basic rendering.
- Any code the agent writes by hand (not generated by a brick) that contains non-trivial
  logic.

---

## 4. Auto-Chaining Rules

| When this brick runs…                   | These test bricks run automatically                                  |
|-----------------------------------------|----------------------------------------------------------------------|
| `feature_complete`                      | `new_usecase_test` × N + `new_repository_test` + `new_bloc_test` × N |
| `new_repository`                        | `new_usecase_test` × N + `new_repository_test`                       |
| `new_page`                              | `new_bloc_test`                                                      |
| `new_usecase` (standalone)              | ❌ Agent must manually invoke `new_usecase_test`                      |
| `new_usecase_with_request` (standalone) | ❌ Agent must manually invoke `new_usecase_test`                      |

---

## 5. `mocktail` Setup Recipe

Every BLoC test or repository test that mocks a method taking a **custom value type** must
register a fallback value in `setUpAll`. Forgetting this raises `MissingStubError` at
runtime.

```dart
class _MockGetByIdCustomerUseCase extends Mock implements GetByIdCustomerUseCase {}
class _FakeGetByIdCustomerRequest extends Fake implements GetByIdCustomerRequest {}

void main() {
  setUpAll(() {
    registerFallbackValue(_FakeGetByIdCustomerRequest());
  });

  late _MockGetByIdCustomerUseCase useCase;

  setUp(() {
    useCase = _MockGetByIdCustomerUseCase();
  });

  test('should_return_DataSuccess_when_usecase_succeeds', () async {
    when(() => useCase(any())).thenAnswer((_) async => DataSuccess(customer));
    // ...
  });
}
```

- Register one `_Fake{Type}` per custom request/entity type used inside `any()`.
- `bloc_test` package is forbidden in this project — use `flutter_test` + `mocktail`.

---

## 6. Test Naming

- Convention: `should_<expected_behaviour>_when_<condition>`.
- Examples:
  - `should_return_DataSuccess_when_datasource_returns_value`
  - `should_emit_CustomerError_when_usecase_fails`
  - `should_validate_form_when_save_pressed`

---

## 7. Test Design

- Test meaningful scenarios and edge cases — not arbitrary coverage targets.
- Each test must have a single, clear assertion focus.
- Prefer many small tests over one big one.

---

## 7b. Fixing Broken Tests — Regenerate vs Hand-Correct

When a structural change (new value object, signature change, renamed field) breaks existing
tests, **prefer regenerating from the test brick** (`new_usecase_test`, `new_bloc_test`,
`new_repository_test`) over hand-patching — it is faster and more token-efficient. **But** the
bricks only generate the **standard generic cases** (the `DataSuccess` / `DataFailed` pass-through
pair with a mock repository). They do **not** reproduce custom assertions — VO invariant checks,
business-rule edges, stock-clamp, status transitions.

Decision rule:

- **Test is purely generic** (only the standard success/failure shape) → **regenerate** via the
  brick. Loses nothing.
- **Test carries custom assertions** the brick can't reproduce → **do not blind-regenerate** —
  regeneration silently deletes real coverage. Either hand-correct, or regenerate the scaffold
  and **re-add the custom assertions on top**.

Never trade token savings for lost coverage. When unsure whether a test is generic, read it
first.

## 8. Tests Are Not Enough

**Tests prove code correctness, not feature correctness.** Especially relevant for:

- **Floor migrations:** tests mock the datasource and never open SQLite. See `data.md §3`.
- **UI flows:** widget tests do not catch runtime errors in real navigation, animations, or
  platform-specific bugs.

For UI changes and any schema-touching change: **launch the app** (`flutter run -d linux`)
and exercise the feature manually before declaring done.

### 8.1 Rendering ≠ working — exercise every element (Zero Tolerance)

A widget appearing in the tree (or in `get_widget_tree` / a screenshot) proves it was
**built**, not that it **works**. "It renders" is never a completion claim. Before declaring a
UI feature done, **interact with every element you added or touched** and confirm the
behaviour, not just the presence:

- **Buttons / taps:** actually trigger them; confirm the resulting navigation, snackbar, or
  state change happens.
- **Dropdowns / selectors / autocompletes:** **open them and confirm they contain options,
  then pick one and confirm the selection sticks.** An empty dropdown still renders perfectly
  and looks fine in the tree — it is the single most common "looks done, isn't" trap.
- **Forms:** submit valid and invalid input; confirm validation and the success path.
- **Lists:** confirm rows appear **with real data**, not just an empty `ListView`.

### 8.2 Data-dependent widgets need data (Zero Tolerance)

Any widget whose content comes from the database (dropdown options, list rows, detail fields)
is only verified when **the underlying table actually has rows**. A feature that depends on a
table no UI populates yet (and that nothing seeds) is **broken on a fresh install**, even
though every test passes and every widget renders.

When you build or touch such a widget, verify the data source:

- Confirm rows exist — query the dev DB directly when in doubt:
  `python3 -c "import sqlite3; print(sqlite3.connect('.dart_tool/sqflite_common_ffi/databases/volta_gestionale.db').execute('SELECT COUNT(*) FROM <table>').fetchone())"`
- If nothing creates the data yet and the feature can't function without it, **seed sensible
  defaults** (Floor `Callback`, idempotent `onOpen` insert-if-empty — see
  `lib/core/database/seed_default_categories.dart`) or build the management UI. Don't ship a
  permanently-empty control.

Reproduce the gap with an **interaction widget test** (tap → open → select → assert), not just
a render assertion. `test/features/consignments/presentation/shared/product_rows_editor_test.dart`
is the reference pattern.
