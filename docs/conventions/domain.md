# Domain Layer Conventions

Read this **before editing any file under `lib/features/*/domain/`**.

Covers: entities, usecases, repository interfaces, exceptions.

---

## 1. Pure Dart Only

- **NO** Flutter imports. **NO** Floor imports. **NO** infrastructure imports.
- The domain layer must compile against pure Dart + `package:equatable`.

---

## 2. Entities — Rich, Not Anemic

Entities own their invariants and behaviour. An **anemic** entity is a bag of public fields
with all the logic living in BLoCs, mappers, or widgets — that is forbidden. Logic lives with
the data it governs.

- All entities are fully immutable: `final` fields only, **no public unguarded setters**.
- Every entity provides a `copyWith` method (generated by the `new_entity` Mason brick).
- Entities extend `Equatable` and declare `props`.
- **Validate in named/factory constructors.** If an entity has invariants (non-negative
  quantity, quantity ≤ stock, non-empty name), enforce them at construction — don't let an
  invalid instance exist.
- **Expose intent-revealing methods**, not raw field math at every call site
  (`cart.addLine(item)`, `line.clampedTo(stock)`, `sale.total`).
- **Use value objects** for constrained concepts (a `Quantity`, a `Money`, a `Code`) instead
  of bare `int`/`String` that any caller can set to a nonsense value.
- **Dates are `DateTime` in the domain**, not strings. A field like `occurredAt` is
  `DateTime`. ISO 8601 string conversion happens only at the data/mapping boundary (model
  `fromEntity`/`toEntity`) — see `data.md §5` and §8 below. Display formatting lives in
  extensions, see `code-quality.md §5`.

### ❌ Wrong — anemic entity, logic leaks into the BLoC

```dart
// ❌ wrong — public fields, no invariants; the BLoC clamps quantity
class CartLine {
  int quantity;            // ❌ mutable, unguarded
  final Item item;
}
// ...in the BLoC:
final qty = requested > item.stock ? item.stock : requested;   // ❌ invariant in presentation
```

### ✅ Correct — entity owns the invariant

```dart
// ✅ correct — invariant enforced where the data lives
class CartLine extends Equatable {
  final Item item;
  final Quantity quantity;

  CartLine._(this.item, this.quantity);

  factory CartLine.of(Item item, int requested) =>
      CartLine._(item, Quantity.clamped(requested, max: item.stock));

  @override
  List<Object?> get props => [item, quantity];
}
```

## 3. Usecases

### Base classes (in `lib/core/utils/use_case.dart`)

- `UseCaseBase<T>` — no parameters: `Future<DataState<T>> call();`
- `UseCaseWithRequest<T, R>` — parameterised: `Future<DataState<T>> call(R request);`

> ⚠️ The class is `UseCaseWithRequest`, not `UseCaseWithParams`. Always extend
> `UseCaseWithRequest` for parameterised usecases.

### Pattern

```dart
// ✅ correct — simple delegation
class GetByIdCustomerUseCase
    extends UseCaseWithRequest<Customer, GetByIdCustomerRequest> {
  final CustomerRepository _repository;
  GetByIdCustomerUseCase({required CustomerRepository repository})
      : _repository = repository;

  @override
  Future<DataState<Customer>> call(GetByIdCustomerRequest request) =>
      _repository.getById(request.id);
}
```

- A usecase is the **only** place where business logic lives: validations, transformations,
  multi-repository orchestration, identity assignment, timestamp stamping, create-vs-update
  decisions. Repositories and BLoCs must not contain business logic. See
  `docs/architecture/use-cases.md` §3 for the worked refactor of Violation 2 (BLoC stamping
  timestamps and assigning IDs).
- For simple delegation (above), the usecase forwards to the repository. That is correct —
  this is the standard pattern even when no extra logic exists, because it preserves the
  abstraction and testability.

### Request classes

- Live in `usecase_folder/model/{name}_request.dart`.
- Naming: `{Method}{EntitySingular}Request` — e.g. `GetByIdCustomerRequest`,
  `UpdateCustomerRequest`.
- Generated by `new_usecase_with_request` brick.

## 4. Repository Interfaces

- Abstract classes only. Implementation lives in `data/`.
- Methods return `Future<DataState<T>>`.
- Repository interfaces are part of the domain — they declare what the domain can request,
  not how it is fulfilled.

```dart
abstract class CustomerRepository {
  Future<DataState<List<Customer>>> getAll();
  Future<DataState<Customer?>> getById(GetByIdCustomerRequest request);
  Future<DataState<void>> create(CreateCustomerRequest request);
  Future<DataState<void>> update(UpdateCustomerRequest request);
  Future<DataState<void>> delete(DeleteCustomerRequest request);
}
```

---

## 5. Exceptions

- Define **feature-specific exceptions** in
  `lib/features/{feature}/domain/exceptions/{feature}_exceptions.dart`. Pure Dart only.
  Pre-approved manual creation (no Mason brick).
- Infrastructure exceptions (`DatabaseException`, `NetworkException`) live in
  `lib/core/utils/exceptions.dart`. Both extend `Exception`.
- Only create a feature-specific exception when the domain meaningfully distinguishes that
  error case (e.g. `MarketNotFoundException`). Do not create speculatively.

---

## 6. Abstractions

Create an abstract class only when testability or substitutability requires it (repository
interfaces, datasource interfaces). Do not add interfaces speculatively.

---

## 7. `DataState<T>` — Sealed Result ADT

```dart
// ✅ correct — sealed ADT, non-null fields per variant
sealed class DataState<T> {
  const DataState();
}
class DataSuccess<T> extends DataState<T> {
  final T data;
  const DataSuccess(this.data);
}
class DataFailed<T> extends DataState<T> {
  final Exception exception;
  const DataFailed(this.exception);
}
```

The abstract base has **no `.data` and no `.exception` fields**. They live on the variants.
`DataSuccess<T>.data` is non-null `T`. `DataFailed<T>.exception` is non-null `Exception`.

### Producers (Repository / UseCase layer)

- Always return `DataSuccess(value)` on the happy path, `DataFailed(typedException)` on
  failure.
- Never throw across the boundary — wrap. BLoCs pattern-match on the result type.
- For void operations: `Future<DataState<void>>` returning `DataSuccess(null)` /
  `DataFailed(...)`.

### Consumers (BLoCs, other use cases)

Destructure the failure with a pattern `if`-case (never `switch` a closed two-case type — see
`bloc-rules.md §10`). The base class has no fields to access, and a bare `is` test does not
promote a field access on a concretely-typed `DataState<T>`.

```dart
// ✅ correct — destructure the failure, then use the cast success
if (result case DataFailed(:final exception)) {
  throw exception;
}

return (result as DataSuccess).data;
```

```dart
// ❌ wrong — base has no `.exception`; this does not compile
emit(XError(result.exception?.toString() ?? 'Unknown'));
```

Full consumer rules + Violation 1 walkthrough:
`docs/architecture/bloc-rules.md` §2.

## 8. Strong Typing for Domain Concepts (Zero Tolerance)

Typed concepts get types. No magic-string or magic-int assignments for things the domain
treats as a closed set or a structured value.

### Statuses are enums, never string literals

```dart
// ❌ wrong — status as a free string; any typo compiles, no exhaustiveness
sale.status = 'COMPLETATA';                      // ❌ magic string (and Italian — see code-quality §9)
if (sale.status == 'COMPLETED') { ... }          // ❌ stringly-typed branch
```

```dart
// ✅ correct — enum, exhaustive switches, no typos
enum SaleStatus { completed, returned, voided }

switch (sale.status) {
  case SaleStatus.completed: ...
  case SaleStatus.returned: ...
  case SaleStatus.voided: ...
}
```

### Time is `DateTime` in the domain

```dart
// ❌ wrong — domain entity stores time as a String
class Sale {
  final String occurredAt;            // ❌ stringly-typed time in domain
}
```

```dart
// ✅ correct — DateTime in the domain; string only at the data boundary
class Sale {
  final DateTime occurredAt;          // ✅ domain holds DateTime
}
// SaleModel.fromEntity / toEntity does occurredAt.toIso8601String() <-> DateTime.parse(...)
```

### Boundary conversion

The **only** place a domain `enum` ↔ `String` or `DateTime` ↔ ISO `String` conversion is
allowed is the data-layer model mapper (`fromEntity` / `toEntity`, see `data.md §5`). The
domain and presentation layers pass the typed value around untouched.

## 9. Value Objects for Constrained Concepts (Zero Tolerance)

A concept with invariants or behavior is **not** a bare `double` / `int` / `String` — it is a
**value object**: an immutable type that validates in its constructor, owns its operations, and
can never be constructed in an invalid state. This is the natural extension of §2 (rich, not
anemic). The data layer maps the value object ↔ primitive at the model boundary
(`fromEntity` / `toEntity`), exactly like enums and `DateTime`.

### Standing rule — check EVERY field of EVERY new entity

This is **not** a fixed list of blessed concepts. **Every time you create or edit an entity**,
go field by field and ask of each primitive (`double` / `int` / `String`):

1. Does it have an **invariant**? (non-negative, bounded range, required format, checksum)
2. Does it have **behavior**? (arithmetic, comparison, formatting, parsing)
3. Is it a **named concept** in the domain, not an incidental scalar?

**Any "yes" → it is a value object, not a primitive.** A bare `int id` or a free-text
`String notes` stays primitive; a `String email` or a `double price` does not. When you
introduce a new VO not already in the codebase, **name it after the concept and propose it** —
don't silently scatter another raw primitive.

### Known value objects (examples, not the whole law)

| Concept                | Replaces                                   | Owns                                                  |
|------------------------|--------------------------------------------|-------------------------------------------------------|
| `Money`                | `double` price / unitPrice / amount        | cents-backed storage, `+`/`multiply`, `format()`      |
| `Quantity`             | `int` quantity / stock                     | non-negative invariant, decrement/clamp              |
| `Email`, `Phone`, `FiscalCode`, `VatNumber`, `ZipCode` | `String` contact/identity fields | format validation at construction                     |

> **Stays primitive (decided):** `Category.discount` / `commission` stay `double` — percentage
> VO was considered and declined. Don't VO-ify scalars with no invariant or behavior; the test
> above is the guard against both extremes.

### `Money` — the canonical example

Store minor units (`int` cents) to avoid float drift; never a bare `double`.

```dart
// ❌ wrong — money as a loose double, arithmetic and formatting scattered everywhere
final double unitPrice;
final total = unitPrice * quantity;
Text('€${unitPrice.toStringAsFixed(2)}');
```

```dart
// ✅ correct — Money value object owns storage, math, formatting, invariant
class Money {
  static const String currencySymbol = '€';

  final int cents;            // minor units — no float drift

  const Money._(this.cents);

  factory Money.fromCents(int cents) {
    if (cents < 0) {
      throw ArgumentError('Money cannot be negative: $cents');
    }

    return Money._(cents);
  }

  factory Money.fromEuros(double euros) => Money.fromCents((euros * 100).round());

  Money operator +(Money other) => Money._(cents + other.cents);
  Money multiply(int quantity) => Money._(cents * quantity);

  String format() => '$currencySymbol${(cents / 100).toStringAsFixed(2)}';
}

// call sites
Text(item.unitPrice.format());
final total = item.unitPrice.multiply(quantity);
```

Because `Money` owns `format()`, money is **never** formatted via a `num` extension
(`code-quality.md §14` — the extension pattern is only for non-domain values).

### Mapping at the data boundary

The model stores the primitive; the mapper converts:

```dart
// SaleItemModel
final int unitPriceCents;                                   // DB column

SaleItem toEntity() => SaleItem(unitPrice: Money.fromCents(unitPriceCents), ...);
SaleItemModel.fromEntity(SaleItem e) : unitPriceCents = e.unitPrice.cents, ...;
```

Apply the same shape to `Quantity` and the contact/identity value objects: validate in the
factory, expose intent-revealing behavior, convert only at the model mapper.
